# G1 29DOF：11k 基线部署

当前默认入口是训练仓库 `unitree_rl_lab_train` 的 **model_10999_factorygait.pt**，来源 TASK_20261020_069。不是后续续训对照或摆臂试验。

**已完成 Windows 上生产 C++ Core/ONNX Runner 的编译、数值对照和 MuJoCo 闭环检查。尚未在 Linux 编译 DDS 主控制器，尚未测试真机。** Linux 构建脚本会在编译后自动运行不连接机器人的推理检查。

## 模型与接口来源

模型及参数随代码一起提交，真机不需要训练仓库、Isaac Lab、PyTorch 或 Python ONNX Runtime。

| 内容 | 项目内实际来源 |
|---|---|
| 起点 checkpoint | `config/policy/velocity/11k/manifest.json` 的 `checkpoint_sha256`、`checkpoint_iter`、`source_task` |
| 原训练机器人参数 | `tools/export_velocity11k.py` 从训练提交 `5421b4f` 与当前训练文件提取并交叉核对 |
| 可读参数 | `deploy/robots/g1_29dof/config/policy/velocity/11k/params/deploy.yaml` |
| C++ 实际使用参数 | `deploy/include/velocity11k/contract.h`，与上述 YAML 一起生成并校验哈希 |
| 数值与闭环检查 | `docs/velocity11k_validation.json`；原始回放 `docs/velocity11k_validation.rollout.csv` |

下表数值来自模型 manifest 的 `contract` 字段和生成的 C++ contract：

| 接口 | 值 |
|---|---|
| ONNX 输入/输出 | float `obs[1,480]` → `actions[1,29]` |
| 周期 | `step_dt=0.02 s` |
| 历史 | 每个观测项独立保留 5 帧，按项拼接，帧从旧到新 |
| 项顺序 | 角速度、投影重力、速度命令、相对默认位关节角、关节速度、上一拍原始 action |
| 缩放 | 角速度 ×0.2；关节速度 ×0.05；action ×0.25 后加默认位 |
| 输入归一化 | 无 empirical normalizer；不要再额外归一化输入 |
| 肩 pitch 默认位 | 左右均 0.3 rad |
| 手臂 Kp/Kd | 40 / 1 |
| 腰部 yaw/roll/pitch Kp | 200 / 40 / 40 |
| 腰部 Kd | 5 |
| 命令边界 | vx [-0.5,1.0] m/s，vy [-0.3,0.3] m/s，wz [-0.2,0.2] rad/s |

命令边界继承训练任务 `limit_ranges`，不是整段范围的真机能力保证。保持原速度控制器的摇杆约定：`vx=ly`、`vy=-lx`、`wz=-rx`，直接按上述物理量范围裁剪，不额外乘最大速度。

`FixStand` 的角度和增益按 SDK 顺序配置；网络使用 articulation/policy 顺序。转换仅通过 `SDK_MAP`，不要将整组数组直接按相同下标互换。`State_Velocity11k` 启动时会拒绝与编译参数不一致的 FixStand 配置。

## 拉取你的部署子分支

以下命令在部署 Linux 电脑执行，仓库目录以 `~/G1_deploy` 为例。子分支名称由你推送时确定，不要拉回 main 覆盖本次适配。

```bash
cd ~/G1_deploy
git status --short
git fetch origin
DEPLOY_BRANCH='替换成你实际推送的子分支名'
git switch "$DEPLOY_BRANCH"
git pull --ff-only origin "$DEPLOY_BRANCH"
python3 tools/check_velocity11k_package.py
```

首次克隆时使用你自己的部署仓库地址，并选择同一个子分支。模型文件是 `deploy/robots/g1_29dof/config/policy/velocity/11k/exported/policy.onnx`，无需从 GM 再下载。

## 编译与不连接机器人的检查

首次安装 Ubuntu 编译依赖：

```bash
sudo apt update
sudo apt install -y build-essential cmake git curl python3 \
  libyaml-cpp-dev libboost-all-dev libeigen3-dev libspdlog-dev libfmt-dev
```

部署代码需要 SDK 头文件 `unitree/dds_wrapper/robots/g1/g1.h`。若已有 SDK，确认此文件存在；缺失时按原仓库的 SDK 安装流程安装对应版本。

```bash
cd ~/G1_deploy
bash tools/build_g1_deploy.sh
```

SDK 安装在非默认位置时：

```bash
UNITREE_SDK_PREFIX=/opt/unitree_robotics bash tools/build_g1_deploy.sh
```

脚本根据实际 CPU 架构选择 ONNX Runtime；默认 Linux 运行库版本为构建脚本中的 `runtime_version=1.22.0`。机载 ARM64 不能使用仓库自带的 x86_64 动态库。首次缺失运行库时从 Microsoft 官方 Release 下载，也可以通过 `ONNXRUNTIME_ROOT` 指定已经安装的对应架构版本。

编译后脚本自动运行 `tools/check_velocity11k_runtime.py`：输入仓库内保存的 NumPy/PyTorch 对照样本，通过真实生产 C++ Runner 推理并比较结果。该检查不初始化 DDS，不连接机器人，也不发送控制指令。失败时不要进入真机运行步骤。

可以再次手动执行：

```bash
python3 tools/check_velocity11k_package.py
python3 tools/check_velocity11k_runtime.py
./deploy/robots/g1_29dof/build/g1_ctrl --help
ldd ./deploy/robots/g1_29dof/build/g1_ctrl
```

`ldd` 中不应出现 `not found`。Windows 上已有检查使用 ONNX Runtime 1.23.2，不能把它当作目标 Linux/ARM 构建与运行已经通过。

## 先用部署控制器做 DDS 仿真

本地检查已经覆盖共用的 C++ 观测、ONNX 与动作转换，但没有覆盖现场 SDK/DDS 通信、线程调度和固件。

部署机安装 `unitree_mujoco` 后，将机器人设为 G1 29DOF，并将仿真 DDS domain 配成 1、启用遥控器。启动仿真后，在部署仓库执行：

```bash
cd ~/G1_deploy/deploy/robots/g1_29dof
./build/g1_ctrl --network lo --domain 1 --config config/config.yaml --log
```

先在该流程核对站立、策略切换、命令方向、停车、退出和日志，再进入真机测试。这里的 `lo/domain 1` 必须与仿真端实际配置一致；真机网卡与 domain 不沿用这组仿真参数。

## 真机受保护测试

由现场人员确认 G1 29DOF 型号、吊装防跌落保护、急停和内置控制程序状态。SDK 的 IMU 坐标约定需要与训练使用的 pelvis IMU 核对。

查看实际机器人网络接口：

```bash
ip -br -4 addr
```

选中实际接口后启动；下面的 `eth0` 需要替换为现场接口：

```bash
cd ~/G1_deploy/deploy/robots/g1_29dof
G1_NET=eth0
./build/g1_ctrl --network "$G1_NET" --domain 0 --config config/config.yaml --log
```

程序启动停在 `Passive`，不会自动进入策略。

| 现场操作 | 行为 |
|---|---|
| L2 + 上 | 从实测关节位置插值到 11k 默认站姿 |
| 等待 `config.yaml` 中的 3 秒站姿过渡完成，并将摇杆回中 | 准备进入策略 |
| R1 + X | 进入固定 11k 的 Velocity 状态 |
| 左摇杆前后 / 左右，右摇杆左右 | 前后 / 侧移 / 转向命令 |
| 摇杆回中 | 零速度命令，策略继续保持运行 |
| L2 + B | 退出到 Passive 阻尼，需要防跌落保护承重 |
| Ctrl+C | 请求发布阻尼后退出进程 |

先验证站立、起步、低速前进与停车。不要用两个后续试验的 checkpoint 替换此模型，也不要在现场叠加摆臂控制。

11k 状态保留原控制器的姿态保护，并沿用已有部署状态的通信/输出 watchdog。失败原因写入日志。该状态没有 BeyondMimic 的参考动作、腿部里程计、默认动作段时限或目标速度限幅器；正常速度策略连续运行，直到现场退出或保护触发。

## 现场日志

文件在 `deploy/robots/g1_29dof/log/`：

- `log.txt`：使用 `--log` 时记录状态、模型来源和退出原因。
- `velocity11k_*.csv`：每次进入策略创建一个文件，记录实测 SDK 关节角/速度、IMU、命令、原始 policy action、发送目标位置和推理耗时。配置 `joint_log: true` 默认启用。

CSV 的 `q_sdk_i` / `dq_sdk_i` / `target_sdk_i` 使用 SDK 顺序；`action_policy_i` 使用 policy 顺序，名称映射在 package manifest 中。没有实测基座平移速度字段，不要把命令速度当作真实速度。

## 检查边界与重新导出

实际结果以 `docs/velocity11k_validation.json` 为准：Windows C++ 数值检查、重入时历史清零、关节目标裁剪、无效四元数拒绝、旧模型拒绝，以及 MuJoCo 命令序列闭环。`hardware_tested=false`、`linux_dds_controller_built=false` 明确保留，现场完成后另记实测结果。

MuJoCo 检查使用训练的显式 PD 和 `effort_limit_sim`。真机发送位置 PD 指令，由固件执行增益和力矩保护；不能将仿真力矩裁剪当作真机已经实现相同的电机行为。转向命令的跟踪仍有限制，见回放的转向段 `actual_velocity_mean`，本次适配不改训练策略。

模型和参数已导出，正常部署不需要重新导出。仅在开发电脑重建本包时使用：

```bash
python tools/export_velocity11k.py --training-root /path/to/unitree_rl_lab_train
python tools/check_velocity11k_package.py
```

导出器只接受已验证 SHA256 的原始 11k checkpoint；同时生成 ONNX、可读 YAML、C++ contract 和 manifest。修改合同参数后必须重新编译、重建对照样本并重新验证，不要仅编辑 YAML。

完整开发验证需要 NumPy、PyTorch、ONNX Runtime；闭环还需 MuJoCo：

```bash
python tools/validate_velocity11k.py \
  --offline-bin deploy/robots/g1_29dof/build/velocity11k_offline \
  --training-root /path/to/unitree_rl_lab_train \
  --closed-loop --xml /path/to/g1_29dof_rev_1_0.xml \
  --output /tmp/velocity11k_validation.json
```

旧 BeyondMimic 包与专用配置仍保留，说明见 `G1_BeyondMimic_部署流程.md`；默认配置没有启用舞蹈状态。
